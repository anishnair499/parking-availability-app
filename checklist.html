What the backend files tell us about the architecture

The ESP32 does not push to Firebase. It serves GET http://192.168.1.42/distance on the local network and returns a number in centimetres. A Python script on some other machine polls that URL, and that script holds a service-account key and writes to Firestore with the admin SDK. Four consequences, all of which change tasks from the last revision:

1. The poller is now the capture single point of failure. It has to run 24/7 on a machine that is on the same WiFi as the sensor — a Raspberry Pi or an old laptop left at the temple — not on Ayaan's Windows laptop at home. If it stops, capture stops, and the ESP32 keeps happily serving a number nobody reads.

2. Security rules get simpler. The admin SDK bypasses rules, so nothing needs public write any more. The “known weakness” from the last revision goes away: every collection can be read-only to clients.

3. The occupancy threshold moves into the poller, not the firmware. The device returns centimetres; the poller decides occupied/free and stores booleans. Same idea, different file.

4. One endpoint means one sensor so far. There is no second IP or second path. Two spots need the ESP32 to return both distances in one response, or two devices.

    CriticalSept 7–10
    What the two files do today

    backend/esp32readings.py defines main() and never calls it — there is no if __name__ == "__main__" block, so running the file does nothing and exits. It is a subset of the other file anyway; delete it or turn it into the shared polling function.

    backend/mlmodeldata.py does call main(), but look at the order: the Firestore .update({"available": False, ...}) at line 33 sits at module level, so it runs exactly once at import, before the loop starts, with a hardcoded False. The loop then polls forever and only prints. The distance reading never reaches the database.     The fix is one file, one loop: read distance → threshold to a boolean → write both documents (next task) → sleep. 60 seconds is a fine interval; the ML resamples to 5-minute buckets anyway.

  • Two writes per poll: append history, overwrite live state
    CriticalSept 7–10
    Why two, and the shape

    Each poll: db.collection("occupancySnapshots").add({...}) for the permanent history the ML trains on, and db.document("current/state").set({...}) for the Parking screen. One overwritten document is one cheap read per client; subscribing to the history collection would bill a read per update and grow forever.

    One document per poll containing every spot, not one per sensor. lstm.py resamples into 5-minute buckets; if spots land in separate documents at slightly different times, buckets lose a value and become NaN, which the new gap logic then treats as an outage.

    {"timestamp": SERVER_TIMESTAMP, "spot_1": True, "spot_2": False}

    Store booleans, decided in the poller: occupied = distance_cm < 30. That literal currently lives five times in parking.tsx:48-58; it belongs here, once, as a named constant.
