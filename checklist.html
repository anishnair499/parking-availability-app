Check the Firestore rules tab today

The database has test documents but no published rules, which means it is almost certainly still in test mode. Test mode is allow read, write: if request.time < timestamp.date(...) — wide open now, and it hard-fails on its expiry date, roughly 30 days after the database was created.

If it was created in mid-August, that expiry lands within days of Sept 6. Every read and write starts returning permission-denied, and the symptoms — writes silently failing, app showing stale data — look exactly like firmware or network bugs. Five minutes to fix now.

Reality check

Sept 6 is a capture deadline, not a code deadline

Only one thing has to work by Sept 6: sensors writing data. Ingestion, ML and every UI fix can be built afterward against readings already banked. Missed readings are the sole unrecoverable failure on this page — you cannot backfill a sensor that wasn't running. Everything in ml/ is trained on synthetic output from gen_fake_data.py until real data accumulates.
But validate early anyway. Get ingest.py reading real data within a few days of Sept 6, then leave it alone. The failure to avoid is discovering on Oct 1 that timestamps are wrong or spots are swapped, with five weeks of unusable rows behind you.

Firmware (critical path) + UI
  • Repoint firmware at Firestore — two writes per poll
    CriticalAug 22–28
    What to write where

    It currently targets Realtime Database. Guide §4a has the REST call — POST to .../documents/occupancySnapshots?key=<API_KEY> with typed values (booleanValue, timestampValue).

    Each poll writes twice: append one document to occupancySnapshots (the permanent history the ML trains on), and overwrite current/state (a single cheap document the live parking screen reads).

    Why two: a live subscription over the history collection bills a read per update per client and grows without bound. A single overwritten document is one cheap read against the 50k/day free tier.

    One document per poll containing every spot — not one document per sensor. The ML resamples into 5-minute buckets, and if spots land in separate documents at slightly different times, buckets lose a value and get silently dropped.

    HighSept 6–13

    The number 5 appears in 8+ independent places with no shared source of truth: ml/lstm.py:27, ml/gen_fake_data.py:24, frontend/app/predictions.tsx:8, and predictions.tsx:129 as a bare literal in JSX ({open} / 5 open).

  • Build the seasonal baseline — it is the launch forecast, not the LSTM
    HighSept 13–27
    The measurements behind this

    An hour × weekday occupancy table (48 numbers per spot) beat the LSTM rollout on every metric on the current data: BCE 0.3255 vs 0.3376, Brier 0.1079 vs 0.1125, accuracy 0.8351 vs 0.8286.

    Important caveat: that was measured on synthetic data whose generator is an hour-lookup table, so it is rigged in the baseline's favour. It does not prove the LSTM is useless on real data.

    What it does establish: the baseline is trivial to build, needs about one week of data instead of three, and the LSTM has to be measured against it before it earns the slot. Separately measured — the LSTM's input window stops influencing the forecast after about an hour (identical output from all-empty vs all-full starting states by step 12), so its value is short-horizon, not week-ahead.

    HighSept 13–27

  • Add cold-start guards — fail loudly on insufficient data
    CriticalSept 6–13
    The silent-garbage bug

    features[-SEQ_LEN:] returns fewer rows when fewer exist, and nn.LSTM accepts variable-length input without complaint. Verified: passing 3 timesteps where 48 were expected returns a clean [1, 5] output with no exception raised.

    So during the first hours after go-live, both entry points will quietly produce confident predictions from almost no data. Assert on window length instead.

  • Handle sensor outages — resampling silently splices across gaps
    CriticalSept 6–13
    Verified behaviour

    resample_occupancy at ml/lstm.py:45 does .resample().mean().dropna(). Fed a 6-hour outage, the output contains two rows 365 minutes apart sitting adjacent — and the model reads them as one 5-minute step.

    Real hardware will have outages. Reindex onto a full time grid, forward-fill short gaps, and refuse to build training windows that span long ones. OccupancyDataset.__getitem__ (lstm.py:66) inherits the same bug — it slices idx : idx+seq_len with no contiguity check.

  • Build the Model tab
    HighSept 27–Oct 10
    What goes on it, in priority order

    The tab’s job is to show the decision, not the architecture. Nobody is impressed by “2 layers, 64 hidden units.” They are impressed by evidence that you measured two approaches and picked one.

    1. Which model is live, and the numbers behind it. Baseline vs LSTM, head to head, on real data, with the serving one marked. Most projects never build a baseline at all — showing that the simple method won, if it does, demonstrates judgement rather than weakness.

    2. Prediction vs reality. Last week’s forecast overlaid on what actually happened. The most honest panel on the page and the one that proves the thing works. Depends entirely on the archiving task above.

    3. Data health. Rows collected, days of coverage, gaps detected, last reading received. Doubles as the only visible check on cron jobs running unattended on a server nobody watches.

    4. Accuracy as data accumulated. A small chart of accuracy against weeks of training data, telling the cold-start story: nothing on Sept 6, baseline online Sept 13, LSTM overtakes it (or does not) around Sept 27. Free if the weekly retrains log their metrics.

    5. How it works. A short ESP32 → Firestore → model explainer. Home gestures at the hardware; this is where the ML half gets explained.

    Feed it from a single models/status document written by the training and forecast jobs — one cheap read, and it makes the cron jobs self-reporting. Do not count documents in occupancySnapshots to get row counts; that bills a read per document.
